02 / REQUEST LIFECYCLE

이미지는 어디서 결과가 될까요?

  1. 입력 검증과 요청 식별

    POST /v1/classify?top_k=5에 multipart file을 보냅니다. 서버가 생성한 UUID는 응답의 request_id, X-Request-ID, Triton 요청 ID, 로그의 request.id로 연결됩니다.

    JPEG/PNG ≤ 10 MiB · top_k 1–10 · 최대 동시 추론 4

  2. FastAPI: 이미지 → FP32 텐서

    EXIF 방향 보정 → RGB → 짧은 변 232로 bilinear resize → 중앙 224×224 crop → 0–1 스케일 → ImageNet 평균·표준편차 정규화 → NCHW 순서로 바꿉니다. 디코딩·리사이즈는 threadpool에서 처리합니다.

    input: [1, 3, 224, 224] · FP32 · 약 588 KiB

  3. Triton: ONNX 모델 실행

    /v2/models/mobilenet_v2/versions/1/infer로 JSON 메타데이터와 binary tensor를 전송합니다. CPU instance 1개, intra-op 2 / inter-op 1 thread로 실행합니다. 고정 batch 1이며 dynamic batching은 설정하지 않았습니다.

    logits: [1, 1000] · FP32 · 4,000 bytes

  4. FastAPI: logits → probability · label

    출력 shape·dtype·유한값·요청 ID를 검사합니다. 1,000개 logits에 안정적인 softmax를 적용하고 top-k class_id를 artifacts/labels.json으로 매핑합니다. Triton은 이 구성에서 레이블이 아닌 logits를 반환합니다.

  5. 응답 반환과 이벤트 기록

    예측값과 단계별 시간을 JSON으로 반환하고 구조화 로그를 기록합니다. Filebeat의 수집·색인을 기다린 뒤 응답하는 구조는 아닙니다. 클라이언트 결과가 먼저 보이고 Kibana에는 뒤이어 나타날 수 있습니다.

로컬에서 호출

curl --fail-with-body \
  -F 'file=@artifacts/sample.jpg' \
  'http://localhost:8000/v1/classify?top_k=5'

03 / LOGGING

“이 요청은 무엇을 예측했나?”

Kibana는 요청 단위의 사실을 찾는 도구입니다. probability와 label은 Triton 로그 옵션을 켜는 것으로 생기지 않습니다. FastAPI의 후처리 완료 지점에서 기록합니다.

1. 한 이벤트, 한 JSON 줄

app/logging_config.py의 formatter가 UTC 시간, 서비스명, 로그 레벨, event UUID를 추가합니다. INFO 성공 이벤트와 실패 이벤트를 stdout 및 공유 볼륨 파일에 기록합니다.

2. Filebeat가 파일만 수집

/var/log/inference/events.jsonl*을 읽습니다. stdout은 Docker 운영 로그용이며 중복 수집하지 않습니다. 파일은 10 MiB마다 회전하고 백업 5개를 보존합니다. 현재 logger는 단일 worker 기준입니다.

3. 파싱 · 식별 · 저장

ndjson의 expand_keys: true가 dotted 키를 객체로 펼칩니다. 256-byte fingerprint로 파일을 구별하고 registry 볼륨에 읽은 위치를 기록합니다. event.id를 문서 ID로 사용해 재전송 중복을 억제합니다.

성공 로그의 핵심 필드 (예시)

{
  "@timestamp": "2026-09-13T00:00:00.000Z",
  "event.id": "이벤트-UUID",
  "event.action": "inference.completed",
  "event.outcome": "success",
  "service.name": "fastapi",
  "request.id": "응답의-request_id",
  "model.name": "mobilenet_v2",
  "model.version": "1",
  "classification.label": "Samoyed",
  "classification.probability": 0.3091233,
  "latency.triton_roundtrip_ms": 14.97,
  "latency.total_ms": 40.95,
  "event.duration": 40950000
}

event.duration의 단위는 ns입니다. 전체 로그에는 classification.top_k와 단계별 지연도 포함됩니다. 이미지 바이트·파일명·API 키는 기록하지 않습니다.

03 시간 범위를 최근 24시간으로 선택

04 아래 KQL로 필터 → 문서 펼치기

classification.label : "Samoyed" and classification.probability < 0.5
event.outcome : "failure"

네 줄은 각각 독립적인 검색 예시입니다. 일자별 색인은 inference-events-yyyy.MM.dd이며 ILM은 색인 생성 후 7일이 지나면 삭제 대상으로 삼습니다. Filebeat 중단 중에는 파일에 누적되지만, 회전 보관량을 초과하면 손실될 수 있습니다. exactly-once를 보장하지 않습니다.

04 / METRICS

“지금 서버는 어떻게 동작하나?”

FastAPI·Triton이 메트릭을 노출하고 Prometheus가 수집합니다. Grafana는 PromQL 쿼리 결과를 그립니다. 요청별 상세 결과와 장기간 성능 추이는 서로 다른 데이터입니다.

운영 질문관측 위치 / 메트릭해석
메트릭을 읽을 수 있나?up{job="api"}, up{job="triton"}1 = scrape 성공. 모델 준비 여부는 /health/ready로 별도 확인
얼마나 요청하나?rate(api_requests_total[1m])초당 요청 수. 추론만 보려면 route 필터
사용자가 느린가?api_request_duration_seconds_buckethistogram 기반 p50 / p95
Triton 왕복이 느린가?api_inference_duration_seconds_bucketFastAPI에서 잰 왕복 추론 p95
큐 또는 계산이 느린가?nv_inference_queue_duration_us / nv_inference_compute_infer_duration_us누적 counter의 증가량을 성공 요청 증가량으로 나눠 평균 ms 계산
어떤 요청이 실패했나?api_requests_total의 status / api_upstream_errors_total메트릭으로 추세 확인 → Kibana failure 이벤트로 상세 조사

FastAPI p95 · 초 → ms

histogram_quantile(0.95,
  sum by (le) (
    rate(api_request_duration_seconds_bucket{
      route="/v1/classify"
    }[1m])
  )
) * 1000

Triton 순수 계산 평균 · μs → ms

rate(nv_inference_compute_infer_duration_us{
  model="mobilenet_v2"
}[1m])
/
rate(nv_inference_request_success{
  model="mobilenet_v2"
}[1m]) / 1000

누적시간 카운터만으로 요청별 p95를 계산할 수 없습니다. Grafana의 Triton 계산·큐 패널은 평균이며, 왕복 p95는 FastAPI histogram 기반입니다. request_id와 분류 label은 메트릭 label로 넣지 않아 시계열 개수가 요청마다 증가하지 않습니다.

No data가 곧 장애는 아닙니다.

요청이 없는 구간에서는 분모가 0이거나 histogram 관측치가 없어 지연값이 비어 있을 수 있습니다. 최근 15분을 선택하고 샘플 요청을 여러 번 보내세요. 현재 구성은 대시보드와 수집을 제공하며 알림 규칙·Alertmanager·외부 알림 채널은 설정하지 않았습니다.

일반 종료 후 다시 실행하는 경우
docker compose down
# 나중에 같은 저장소 디렉터리에서:
docker compose up -d
docker compose ps -a
curl --fail http://localhost:8000/health/ready
curl --fail-with-body -F 'file=@artifacts/sample.jpg' \
  'http://localhost:8000/v1/classify?top_k=5'

매번 export하거나 .env를 새로 만들 필요가 없습니다. 모델과 artifacts가 존재해야 합니다. 컨테이너 상태가 healthy여도 모델은 언로드 상태일 수 있으므로 ready와 실제 분류까지 확인합니다. observability-init의 Exited (0)은 정상입니다.

설정·모델을 수정한 경우
# API 코드·의존성 변경
docker compose up -d --build api
# .env 환경변수 변경
docker compose up -d --force-recreate api grafana
# 마운트된 수집 설정 변경
docker compose restart filebeat prometheus grafana
# ES template / Kibana 저장 객체 변경
docker compose run --rm observability-init
# 모델 재생성: 요청을 멈춘 뒤 실행
docker compose stop api triton
docker compose run --rm model-export
docker compose up -d triton api

restart는 새 이미지나 변경된 컨테이너 환경변수를 적용하지 않습니다. Grafana의 기존 관리자 비밀번호는 DB에 남으므로 .env 수정·재생성만으로 바뀌지 않습니다. ES의 기존 필드 타입도 template 변경만으로 바뀌지 않으며 새 색인/재색인 검토가 필요합니다.

데이터를 삭제하고 완전히 초기화하는 경우
실행하면 저장된 요청 로그·메트릭·Grafana 사용자 설정이 삭제됩니다. 필요한 데이터는 먼저 백업하세요.
docker compose down -v
docker compose up -d
docker compose ps -a
curl --fail http://localhost:8000/health/ready

호스트의 artifacts/, model_repository/, .env와 Docker 이미지는 남습니다. 따라서 파일이 존재하면 재export 없이 시작합니다. Kibana 객체와 Grafana provisioning은 다시 생성됩니다. 컨테이너 볼륨의 과거 추론 이력은 복원되지 않습니다.

컨테이너 종료와 모델 언로드는 다릅니다.

FastAPI의 관리자 API는 Triton 내부 모델을 로드·언로드합니다. Docker 컨테이너 시작·종료는 Compose가 담당합니다. 모델 언로드는 프로세스를 내리지 않으며 live 200 / ready 503 / classify 503이 됩니다.

06 / DIAGNOSIS

증상에서 원인으로 좁혀 갑니다.

API 503

서버인가, 모델인가?

live → ready 순으로 확인합니다. 모델이 언로드되었으면 관리자 load를 호출합니다. Triton 로그와 ONNX 파일 존재 여부를 확인하세요.

docker compose logs --tail=100 triton api
KIBANA EMPTY

생성 → 수집 → 색인 → 검색

실제 요청을 보낸 뒤 API 로그, Filebeat 로그, init 종료 코드를 봅니다. 최대 60초 기다리고 data view·시간 범위·request.id 필터를 확인합니다.

docker compose logs --tail=100 api filebeat observability-init
GRAFANA NO DATA

scrape 성공부터 확인

Prometheus Targets에서 api/triton UP 확인 → 연속 추론 생성 → 최근 15분으로 조회합니다. 모델 언로드 중에는 해당 모델 메트릭이 사라질 수 있습니다.

docker compose logs --tail=100 prometheus grafana
429 / 504

부하인가, upstream 지연인가?

429는 동시 추론 제한 초과입니다. 504는 Triton 호출 timeout입니다. inflight, 큐 평균, 계산 평균, 왕복 p95를 비교하고 failure 로그를 조회합니다.

api_inflight_requests · api_upstream_errors_total

장애 구간의 차이

Filebeat가 중단되면 API는 파일에 계속 기록하며 재시작 후 수집을 따라잡습니다. Elasticsearch 중단은 로그 조회·전송에 영향을 줍니다. Prometheus 중단 구간의 메트릭은 나중에 소급 수집되지 않습니다. Triton이 준비되지 않으면 이미지 분류가 실패합니다. 이 구성은 단일 노드이므로 고가용성을 제공하지 않습니다.
